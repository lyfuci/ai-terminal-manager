## 讨论的演进路径

1. **出发点**：想做 terminal 管理程序 —— 自由布局、记住状态、左侧可收纳窗口能快速打开最近对话到指定分窗口。
2. **拆出三层状态（L1/L2/L3）** → 认定 L2（进程活过 UI）是真正的分岔点，自己管 PTY 做不到。
3. **用户选择**：L2 必需 → tmux 当后端；运行形态 → Windows 原生 GUI 连进 WSL。
4. **查证 tmux 控制模式**（man tmux 3.6）→ 确认协议可用，并发现两个刚好命中场景的特性。
5. **用户追问「tmux 是什么协议？你是觉得 tmux 改动的工作量比较小对吗？」**
   → **纠正了一个错误暗示**：推荐 tmux 不是因为省事，它前期工作量更大；买的是 L2 + 跨端接管。
   → 补出**第三条路：自写常驻 daemon**（拿到 L2 且布局完全自由，没有「两份布局真相同步」这个最脏的部分）。
6. **用户追问「进程本身关了会影响吗？」** → 查本机实际配置，收窄了 L2 的边界（保不住 `wsl --shutdown`）。
7. **用户判断「tmux 布局能力可能已经够了」** → 确认这个判断成立，于是提出**路线 C：先别写 app**，
   整个构想可能缩成几百行的 tmux 侧栏。
8. 会话停在这里（用户在 `~/.claude/projects/-home-user` 里敲了个 `pwd`），**A/B/C 未拍板**。

## 过程中被修正的判断（重要 —— 别把中间态当结论）

| 中途说法 | 修正 |
|---|---|
| 「推荐 tmux」隐含省事 | ❌ tmux **前期工作量更大**；理由只有 L2 + 跨端接管 |
| 「别用 TCP 端口，走 wsl.exe stdio」 | ⚠️ 因 本机 WSL 的 localhost 互通，TCP 其实可行；stdio 仍更省事（无端口/防火墙/鉴权） |
| 只有 tmux / 自管 PTY 两条路 | ❌ 还有自写 daemon（第三条）和「先不写 app」（第四条） |
| L2 = 状态永远不丢 | ❌ 保不住 `wsl --shutdown` / Windows 重启，那时只能靠 L3 降级 |
| tmux-resurrect 能恢复会话 | ⚠️ 它给的是 **L1 + cwd**，是**重新拉起进程**，不是恢复进程状态 |

## 当时提的架构草案（走 tmux + GUI 路线时）

```
Windows 侧 (Tauri + xterm.js)
        │  stdio JSON-RPC，单一通道
        ▼
wsl.exe -d <distro> -- node agent.js     ← WSL 里的常驻助手
        ├── tmux -CC  (控制模式子进程)
        └── inotify 监听 ~/.claude/projects/ 和 ~/.codex/session_index.jsonl
```

agent 生命周期跟 GUI 绑定，**tmux server 独立于 agent 存活** —— 这正是要的 L2。

布局的现实边界：tmux 是二叉分割树，`#{window_layout}` 给出 `bb62,208x50,0,0{104x50,0,0,1,...}` 这种串，
**存这个串就等于存了布局**。能做任意比例的矩形网格，**做不到浮动/重叠**。
交互设计要按「拖分割线」而不是「拖窗口」来想。

## 悬而未决的那个问题

> **你需不需要从别的地方（纯 SSH 进来、手机、另一台机器）接管同一批会话？**

- 需要 → tmux，那份布局同步的脏活值得。
- 不需要 → 自写 daemon，拿回自由画布，总复杂度更低。
