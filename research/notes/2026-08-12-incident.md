# 2026-08-12 WSL 冻结事故 · 取证记录

> 写这份的首要目的是**记下一个被推翻的诊断**。第一版结论（「atm 让用户 resume 了巨型会话把内存打爆」）
> 被证据否掉了，但它一度被我写死进了 `src/atm/dispatch.py` 的注释里当成产品事实。
> 教训与 `idea-log.md` 里那条「Search Before Asserting」是同一个。

## 现象

用户：「我刚想 detach 我的 main 会话，然后直接硬盘就疯狂写入，系统就卡死重启了。」

## 已确证的事实

### Windows 侧（决定性证据，来自事件日志）

| 时间 | 事件 | 含义 |
|---|---|---|
| 08:01:36 | **Event 1074 (User32)**，`StartMenuExperienceHost.exe`，原因「其他(计划内)」，类型「重启」 | **是用户从开始菜单手动点的重启** |
| 08:02:23 | Kernel-Power 109，`Power Action Reboot`，Reason `Kernel API` | 正常的重启流程 |
| — | **无 Event 41**（意外关机）、**无 Event 1001**（bugcheck / 蓝屏） | **Windows 从未崩溃，也没自动重启** |

结论：这是**卡死（hang）**，不是崩溃重启。WSL guest 在 07:54:04 就没日志了，用户等到 08:01 手动重启。

### 宿主资源（这才是根本背景）

- 物理内存 **15.7 GB**；重启后刚开机就只剩 **2.3 GB 可用**
- 常驻大户：`vmmemWSL` 3.88GB、`work-chat`(企业聊天软件) 1.5GB + `work-chat-web` 0.5GB、`svchost` 1.79GB、
  **`Memory Compression` 0.9GB ← Windows 已经在压缩内存，本身就是内存吃紧的信号**
- 提交上限 53.7GB（页面文件很大）→ 所以**不会**触发 Event 2004 资源耗尽，
  只会**一路狂刷页面文件** —— 这与用户看到的「硬盘疯狂写入」完全吻合

### WSL 侧

- `.wslconfig` 给 WSL 上限 6GB；实测 WSL 内 `buff/cache` 轻易涨到 4GB+
- **WSL 的页缓存在 Windows 看来就是 vmmemWSL 的真实内存占用**（直到 autoMemoryReclaim 还回去）
- 崩溃窗口（07:40–07:55）内，**整个 home 目录只有一个 >1MB 的文件被写过**：
  一条 7.4MB 的 Claude 会话转录（07:50:15）
  → **WSL 文件系统内根本没有写入风暴**，磁盘狂写发生在宿主侧的页面文件

## 被推翻的第一版诊断

原结论：atm 让用户一键 resume 了 649MB 的会话 → Claude Code 整个读进内存 → 打爆 6GB 的 VM。

推翻它的证据（其中三条是 codex 独立评审指出的）：

| 我的论据 | 为什么不成立 |
|---|---|
| 「`~/.cache/atm/index-v1.json` mtime=07:45:33 证明 atm 投递过」 | **只能证明 atm 跑过**。`atm list` / `doctor` / 打开 TUI 又取消 都会无条件重写缓存 |
| 「日志里的 `drop_caches` 是内存压力信号」 | **读反了**。`autoMemoryReclaim=gradual` 是 **CPU 闲置约 5 分钟后**的例行回收，方向上反而说明当时系统很闲 |
| 「崩溃前 resume 了巨型会话」 | 崩溃前 4 分钟真正被动过的会话**只有 7.4MB**。这条数据我自己查出来了，却因为不符合理论跳过去了 —— 确认偏误 |
| 「`--resume` 会把整个 jsonl 读进内存」 | **从未验证**。claude 二进制里有 `createReadStream` / `transcript ranged read` 字样，至少足以否定这个确定性表述 |
| 「Windows 崩溃重启了」 | 事件日志显示是**用户手动重启**，无 41 / 无 1001 |

## 目前最站得住的解释（仍是假说，未坐实）

宿主 15.7GB 本就长期只剩 2~3GB 可用（企业聊天软件 + 浏览器 + svchost 占掉一大半），
WSL 上限 6GB。**任何在 WSL 里大量读文件的操作都会把 vmmemWSL 顶向 6GB**
（页缓存算进 VM 占用），宿主随即进入压缩 + 页面文件狂刷 → 整机无响应。

⚠️ 注意这里的因果与 atm 的关系：**不是**「claude 把大文件读进内存」，而是
**「在 WSL 里读大量文件」本身就会顶高 vmmemWSL**。按这个机制，嫌疑更大的是当时正在跑的
大批量文件读取（例如对 295MB 的 claude 二进制反复 `strings`），而不是 atm 的索引
（实测冷启动只读 47MB）。

**未取证的部分**：07:54 那一刻具体是谁把内存顶上去的，没有证据。宿主侧没有留下
per-process 的内存时间线，事后无法还原。

## 对 atm 的实际影响

1. 体积闸门（20MB 警告 / 100MB 拦截）**保留，但降级为「保守策略」，不再宣称是事故修复** ——
   它对这次事故（7.4MB）完全不会触发。
2. 真正成立的、与事故无关的原则仍然是：**atm 不知道下游 CLI 打开一条会话要花多少资源**，
   代价由别人承担。给异常大的会话一个提示是合理的。
3. 阈值是**拍的**，没有实测支撑。该做的是在独立 cgroup 里分桶实测
   claude 打开各尺寸会话的峰值 RSS，而不是在 6GB 的工作机上直接复现 649MB。
4. codex 建议的结构性方案比阈值可靠：**把 claude 放进带 `MemoryMax` 的 cgroup**，
   顶到上限只杀 claude，不拖垮整个 WSL。

## 顺带查清的：转录为什么这么大

用户问「是因为有多媒体文件吗？」—— **不是**。流式分析（`research/experiments/2026-08-12-transcript-bloat/`）：

| 会话 | 大小 | hook 记录占比 | 多媒体占比 |
|---|---|---|---|
| session-a (sample-sync) | 649MB | **83.7%** | 0.9% |
| session-b (「你好呀」) | 126MB | **78.2%** | 1.2% |

真凶是 **ECC（everything-claude-code）插件的 hook**：每次工具调用都把
`command` / `stdout` / `stderr` 完整写进 `type:"attachment"` 记录；
`async_hook_response` 里 **`response` 和 `stdout` 是同一份 JSON 存了两遍**。
平均每条 hook 记录 10KB，649MB 那条里有 55,923 条。

ECC 已于 2026-08-06 移除（全局 CLAUDE.md 有记录），本机已无安装痕迹 →
**这是历史包袱**，649MB 那条最后改动停在 08-04。当前会话已恢复正常量级（本会话 2.0MB）。

## 实验台先决条件：刹车必须先被验证

`guard.py` 持续采样 PSI / buddyinfo / swap / MemAvailable，越线立刻 SIGKILL 整个 cgroup。
上线前做了 7 项自检（4 项端到端 + 7 条决策逻辑单测），**包括真的让它刹住一次**：

- 正常命令不误停 ✓
- 硬性时限能刹住 ✓
- 用户 `touch /tmp/atm-experiment-abort` 能刹住（0.0s 生效）✓
- 健康指标能刹住（用不可能的阈值触发，0.04s 生效）✓
- 刹停后无残留进程 ✓

## 实验 1：碎片化假设（对照组）

| 组 | order≥6 空闲块 开始→结束 |
|---|---|
| A 静置基线 | 304 → 278 |
| B 稳态持有 1GB | 278 → 291 |
| **C 高频翻搅 500MB** | 291 → **434** |

**翻搅组的连续大块不降反升。** 事后想很合理：整块分配-释放会把大段连续物理页
还给伙伴系统，**反而在整理碎片**，而不是制造碎片。

## 实验 2：直接复现事故负载（反复拉起/杀掉 claude ×4）

| 指标 | 基线 → 结束 |
|---|---|
| order≥6 连续块 | 369 → **403（+34）** |
| swap 使用 | 0.0% → **0.0%** |
| 可用内存 | 86.8% → 86.6% |
| 被健康指标刹住 | **0 / 4 轮** |

claude 单进程峰值 242–244MB，与 systemd 记账的 254.7MB 吻合。

## 结论：我的因果解释被推翻，但真因仍未定

「反复申请释放大块内存 → 物理内存碎片化 → VMBus 拿不到 order:6」这条链，
**在合成负载和真实负载上都不成立**。这是本次事故我给出的第三个被推翻的解释。

⚠️ **这不等于证明了别的东西**。复现失败有两种可能，现有证据分不开：

1. 负载本来就不是原因（我一直在错怪它）；
2. 配置改动已经移除了真正的触发条件 —— 现在是 **8GB + autoMemoryReclaim=disabled**，
   而事故时是 **6GB + 实际生效的 dropCache**（那句 `gradual` 写错了段、从未生效）。
   实测佐证：改配置后 `drop_caches` 次数从「每 60 秒一次」变成 **0 次**。

要分开这两种可能，得把配置改回 6GB + dropCache 再复现一次 ——
**不做**，风险是再死一次机器，收益不值。

## 本次事故我犯的错，按时间顺序

1. 把「resume 会把整个转录读进内存」当事实 → 据此加了字节级闸门（实测 resume 只贵 5~22%，闸门已删）
2. 把索引缓存 mtime 当成「atm 投递过」的证据（其实 list/doctor 都会重写它）
3. 把 `drop_caches` 读成内存告急信号（它其实是 autoMemoryReclaim 的例行行为）
4. 自己查出「崩溃前只动过 7.4MB 的会话」这条反证，却因为不合理论跳过去了
5. 把 order:6 分配失败当根因说满（未证实，且复现不出来）
6. 注释掉 `autoMemoryReclaim=gradual` —— 实为回落到更激进的默认值 `dropCache`

**六次里有四次是 codex 或实测把我拉回来的。** 教训不是「要更小心」，
而是**在有刹车之前不要跑会伤机器的实验**，以及**负面结果先怀疑测量本身**
（见 `research/experiments/2026-08-12-resume-cost/PITFALLS.md`，同一个脚本我写错了五次）。

## 附二：codex exec「假死」—— 结案（2026-08-12）

### 真因只有一个，`< /dev/null` 是完整解，不是缓解

`codex exec --help` 原文写明：

> If not provided as an argument (or if `-` is used), instructions are read from stdin.
> **If stdin is piped and a prompt is also provided, stdin is appended as a `<stdin>` block**

即 argv 已经给了 prompt，codex **仍然**要读 stdin 到 EOF。挂在不 EOF 的管道上就永久
阻塞在 `read(2)` —— 睡眠态、零 CPU、无输出，这正是「假死」的观感。

上游已确认，不是我们环境的问题：
[openai/codex#20919](https://github.com/openai/codex/issues/20919)、
[#27019](https://github.com/openai/codex/issues/27019)。`< /dev/null` 是官方认可的绕法；
有人在提 `--no-stdin` 提案，截至 0.147.0 **尚未提供**。

### 我此前那条「长 prompt 加了 `< /dev/null` 还是会挂」是错的

实测四组（每组带 `timeout`，rc=124 = 被强杀 = 真挂住）：

| 组 | 场景 | rc | 耗时 |
|---|---|---|---|
| A | 短 prompt 走 argv，`< /dev/null` | 0 | 10.1s |
| B | 40KB 长 prompt 走 argv，`< /dev/null` | 1 | 35.7s，`ERROR: Selected model is at capacity` |
| C | 同样 40KB 走 stdin（管道会 EOF） | 0 | 8.0s |
| D | 短 prompt 走 argv，stdin 是永不 EOF 的 FIFO | **124** | 卡在 `Reading additional input from stdin...` |

B 看着像失败，**但它没有挂** —— 35.7s 后正常返回了服务端的 capacity 错误。
同样的长 prompt 重跑 3 轮（`--json`），**3/3 全部成功**，8.5s / 8.9s / 14.2s，
事件流完整（`thread.started → turn.started → item.completed → turn.completed`）。

所以「长 prompt 会挂」是**归因错误**：真实情况是撞上服务端 capacity / 排队时
codex 静默等待或重试，期间同样零 CPU、零输出，**肉眼与 stdin 死锁无法区分**，
于是被我归成了同一种病。这是本次事故里第七次「症状相似就当同一个根因」的错误。

### 长 prompt 真正的墙：单串 argv 128KB，不是 ARG_MAX

```
单个 argv 127KB -> ok
单个 argv 128KB -> E2BIG（失败）
getconf ARG_MAX = 2097152   ← 这是**总和**上限，不是单串上限
```

`MAX_ARG_STRLEN` 是独立的 128KB 硬上限。超过是**报错**（E2BIG）不是挂，
但意味着大 prompt 必须走 stdin 而不是 argv。

### 固定调用协议（照抄即可）

```bash
# 短 prompt：走 argv，显式给 stdin 一个立即 EOF
timeout --signal=TERM --kill-after=5s 120s \
  codex exec --ephemeral --skip-git-repo-check -s read-only -C "$dir" "$prompt" \
  </dev/null >codex.out 2>codex.err

# 长 prompt（>100KB 或含复杂引号/换行）：走 stdin，用 `-` 显式声明
timeout --signal=TERM --kill-after=5s 300s \
  codex exec --ephemeral --skip-git-repo-check -s read-only -C "$dir" --json - \
  <"$prompt_file" >events.jsonl 2>codex.err
```

要点（后三条是 codex 自己复核时补的）：

- **不要用 `0<&-` 代替 `</dev/null`**：关闭 fd 让 `read(0)` 返回 `EBADF`，
  `/dev/null` 才是正常的 EOF，更符合 CLI 预期。
- `timeout` **不要加 `--foreground`**，否则它管不了整个进程组；`--kill-after` 兜住不理 TERM 的情况。
- **stdout / stderr 必须分开存**：普通模式下进度信息本来就在 stderr。
- `--json` 能把「卡在哪一段」分类，但**不是可靠的重试指示器**（内部退避计时器没有公开事件）：
  - 连 `thread.started` 都没有 + `Reading additional input from stdin...` → stdin 死锁；
  - 已有 `turn.started` 后沉默 → 越过了 prompt 读取，是 API / 排队 / 生成 / 重试；
  - 出现 `error` / `turn.failed` → 直接分类。

`--ephemeral` 是我加的：不往 `~/.codex` 写会话文件，符合「会话数据只读」的约定。

## 附三：内存保护被 resurrect 绕过 —— 已修（2026-08-12）

### 问题

atm 投递时裹 `systemd-run --user --scope` 加限制，但 **systemd-run 是过渡进程，`ps` 看不到它**。
tmux-resurrect 存的正是 `ps` 看到的命令行，所以存档里是裸的 `claude --resume <id>`。
于是 **continuum 开机批量恢复出来的会话一个限制都没有** —— 而那恰是最危险的时刻。

实测证据：

```
app-tmux.slice  memory.peak = 6.75 GB      WSL 总内存 = 7.8 GB
tmux server 自己在 /init.scope，不在这个 slice 里
```

光 tmux 里的进程就峰值吃掉 87% 内存，这就是两次冻死的直接原因。

### 修法（双层，两条拉起路径汇合到同一个池）

1. `~/.config/systemd/user/atm-ai.slice` —— **总量**闸门 `MemoryHigh=4G / MemoryMax=5G / Swap=1G`
2. `~/.local/bin/ai-scope` —— 把单个进程放进 `atm-ai.slice` 并加 `2G/4G/512M` 单进程闸门
3. `~/.tmux.conf` 的 `@resurrect-processes` 用 **`->` 命令替换**让恢复走 wrapper：

   ```tmux
   set -g @resurrect-processes '"~claude->$HOME/.local/bin/ai-scope claude *" "~codex->$HOME/.local/bin/ai-scope codex *" "uv"'
   ```

   `->` 的语义：恢复时改用箭头右边的命令，`*` 展开存档里的原参数
   （官方 `docs/restoring_programs.md:26-33, 93-98`，本机 `process_restore_helpers.sh:116` 确认）。
4. `dispatch.py` 加 `--slice=atm-ai.slice`，让 atm 日常投递的会话也进同一个池。

关键点：**wrapper 不需要对 `ps` 可见** —— `->` 是恢复时替换，不依赖存档内容。

### 端到端验证（独立 socket，用 sleep 当替身）

```
存档里记的        sleep 4321            ← 裸命令，wrapper 确实不可见
恢复后的 cgroup   .../atm.slice/atm-ai.slice/run-p1821110-i1821644.scope   ✅
单进程限制        memory.high=2G  memory.max=4G                            ✅
```

### 测试自身踩的两个坑（都写进脚本注释了）

1. **独立 socket 的 tmux server 照样 source `~/.tmux.conf`** ——
   `@continuum-restore on` 于是把用户的存档整个恢复进测试 server（实测一次拉起 5 个 claude）。
   **必须 `-f /dev/null`**。这也意味着：用户环境里**任何**新起的 tmux server 都会触发一次全量恢复。
2. `kill-session` 杀掉**唯一**会话会连 server 一起销毁，设在 server 上的 `@resurrect-dir` 随之消失，
   restore 回落到默认目录（= 用户的真实存档）。必须先建占位会话。

### 没做的部分

`loginctl enable-linger` 需要 sudo，且会改变「最后一个 login session 退出后用户进程是否存活」的全局语义。
当前 `Linger=no`，实测会话能跨 detach 存活，没有实际问题 —— 留给用户决定。
